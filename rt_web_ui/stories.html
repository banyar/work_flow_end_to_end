Story များ (S1–S11)

S1 လုပ်ခွင့်ရှိတဲ့ ticket တွေကိုပဲ ယူပြီး ticket တိုင်းကို မှတ်တမ်းတင်Eligible tickets are picked up and every ticket is recorded #22949 New 5 AC BaNyar Sithu
ရိုးရှင်းစွာ ပြောရရင်

Automation ရဲ့ အဝင်တံခါးပါ။ NOC queue ထဲ ရောက်လာတဲ့ ticket တိုင်းကို မလုပ်ပါဘူး — service အမျိုးအစား မှန်ရမယ်၊ OPI customer မဖြစ်ရဘူး၊ CPE ID နဲ့ Local Service ID ပါရမယ်၊ status က new / in progress / reopen ဖြစ်ရမယ်။ မလုပ်တဲ့ ticket ဖြစ်ဖြစ်၊ ဘာကြောင့် မလုပ်လဲ ဆိုတာကိုပါ မှတ်တမ်းတင်ရပါတယ်။ ဒါမှ ticket တစ်ခုမှ တိတ်တိတ်ဆိတ်ဆိတ် ပျောက်မသွားမှာပါ။ S2 နဲ့ အတူ walking skeleton (အရင်ဆုံး ဆောက်ရမယ့် အခြေခံ အပိုင်း) ဖြစ်ပါတယ်။

As a NOC Manager, I need only eligible tickets to enter the automation, with each ticket and any skip reason recorded, so that the automation acts only where intended and no ticket disappears silently.

  1. AC01Eligible service typesNOC queue ထဲက MNet၊ MNet Plus၊ G2 Net၊ G2 Plus customer ticket ကို အလိုလို process လုပ်တယ်။A ticket assigned to the NOC queue for an MNet, MNet Plus, G2 Net or G2 Plus customer is processed automatically.
  2. AC02OPI exclusionOPI customer ticket ကို automation က မလုပ်ဘူး။A ticket for an OPI customer is not processed by the automation.
  3. AC03Required identifiersCPE ID ဒါမှမဟုတ် Local Service ID မပါရင် မလုပ်ဘူး၊ အကြောင်းရင်းကို မှတ်တယ်။A ticket without a CPE ID or Local Service ID is not processed, and the reason is recorded.
  4. AC04Eligible ticket statusStatus က new / in progress / reopen (config) ဖြစ်မှ လုပ်တယ်။Only tickets in an eligible status are processed (config accepts new, in progress, reopen).
  5. AC44Every ticket has a recordNOC ကို ဝင်လာတဲ့ ticket တိုင်းမှာ မှတ်တမ်း ရှိရမယ် — စစ်ခဲ့တဲ့ rule၊ ကိုက်တဲ့ criteria၊ ဆုံးဖြတ်ချက်၊ action၊ integration ရလဒ်၊ fail အကြောင်းရင်း၊ final status။Every ticket entering the NOC has a transaction record: rules evaluated, criteria matched, decision, actions, integration results, failure reason and final status.

S2 Network ကောင်းပြီး rule တစ်ခုမှ မကိုက်ရင် Remote Resolve လုပ်A ticket with a healthy network and no special category is remotely resolved #22950 New 6 AC BaNyar Sithu
ရိုးရှင်းစွာ ပြောရရင်

ပုံမှန်လမ်းကြောင်းပါ။ CPE/network data ကို ယူပြီး rule တွေကို သတ်မှတ်ထားတဲ့ အစဉ်အတိုင်း စစ်ပါတယ် — ပထမဆုံး ကိုက်တဲ့ rule က ဆုံးဖြတ်ပါတယ်။ Network rule တစ်ခုမှ မကိုက်မှ (network ကောင်းမှ) category rule တွေကို စစ်ပါတယ်။ ဘာ rule မှ မကိုက်ရင် ticket ကို Customer Support ဆီ ရွှေ့ပြီး resolved လုပ်၊ Remote Resolve field တွေနဲ့ comment ကို RT ထဲ ရေးပါတယ်။ S5–S8 က ဒီ rule order နဲ့ RT update ကို ပြန်သုံးပါတယ်။

As a NOC engineer, I need a ticket whose network is healthy and which matches no special rule to be remotely resolved automatically, so that routine tickets no longer need manual handling.

  1. AC08CPE data retrievedCPE ID မှန်ရင် CPE နဲ့ network data ကို အလိုလို ယူတယ်။For a ticket with a valid CPE ID, the required CPE and network data is retrieved automatically.
  2. AC32Remote Resolve defaultဘာ rule မှ မကိုက်ရင် Remote Resolve — Customer Support ဆီ ရွှေ့၊ resolved၊ Remote Resolve field တွေနဲ့ comment ရေး။When none of the network and category rules match, the ticket is remotely resolved: moved to Customer Support, resolved, with the Remote Resolve fields and comment.
  3. AC33Category rules gatedCategory rule တွေကို network ကောင်းမှ (network rule မကိုက်မှ) စစ်တယ်။Category rules run only when the network is good (no network rule matched).
  4. AC34Rule orderRule တွေကို သဘောတူထားတဲ့ အစဉ်အတိုင်း စစ်ပြီး ပထမဆုံး ကိုက်တဲ့ rule က ဆုံးဖြတ်တယ်။Rules are applied in the agreed order and the first match decides the action.
  5. AC36Status per ruleRule တစ်ခုစီက သူ့အတွက် သတ်မှတ်ထားတဲ့ status ကို ထားတယ် (ဒါမှမဟုတ် မပြောင်းဘူး)။Each rule sets the ticket status agreed for it (or leaves it unchanged).
  6. AC37RT ticket updatedရွေးလိုက်တဲ့ action အတိုင်း RT မှာ queue၊ field နဲ့ comment ကို update လုပ်တယ်။The ticket's queue, fields and comment are updated in RT to match the chosen action.

S3 ၂၄ နာရီအတွင်း NOC ကို ပြန်ရောက်လာရင် ထပ်မလုပ်A ticket re-assigned within 24 hours is not processed twice #22951 New 3 AC BaNyar Sithu
ရိုးရှင်းစွာ ပြောရရင်

Ticket တစ်ခုကို process လုပ်ပြီး ၂၄ နာရီအတွင်း NOC ကို ပြန်ရောက်လာရင် ထပ်မလုပ်ဘဲ ကျော်ပါတယ် (customer တစ်ယောက်ကို ခဏခဏ မထိအောင်)။ ၂၄ နာရီ ကျော်ပြီးမှ ပြန်ရောက်ရင်တော့ ပြန်လုပ်ပါတယ်။ ကျော်လိုက်ရင် ဘာကြောင့် ကျော်လဲ ဆိုတာကို မှတ်တမ်းတင်ရပါတယ်။ (Acceptance page မှာ ADM-09 က ဒါကို စစ်ပါတယ်။)

As a NOC engineer, I need a ticket assigned to the NOC again within 24 hours of being processed to be skipped, so that the same customer is not processed repeatedly.

  1. AC05Duplicate within 24 hoursProcess လုပ်ပြီး ၂၄ နာရီအတွင်း NOC ကို ပြန်ရောက်ရင် ကျော်တယ်။A ticket assigned to the NOC again within 24 hours of being processed is skipped.
  2. AC06Duplicate after 24 hours၂၄ နာရီ ကျော်ပြီးမှ ပြန်ရောက်ရင် ပြန် process လုပ်တယ်။A ticket assigned to the NOC again after 24 hours is processed again.
  3. AC07Skip is recordedDuplicate လို့ ကျော်ရင် အကြောင်းရင်းနဲ့ cache အချက်အလက်ကို မှတ်တယ်။When a ticket is skipped as a duplicate, the skip reason and cache information are recorded.

S4 CPE data မရရင် Manual Check လို့ မှတ်A ticket whose CPE data cannot be retrieved is flagged for Manual Check #22952 New 4 AC BaNyar Sithu
ရိုးရှင်းစွာ ပြောရရင်

Node-RED ကနေ CPE data မရရင် မှားပြီး အလိုလို resolve မလုပ်မိအောင်၊ ticket မပျောက်အောင် ထိန်းတာပါ။ Request တစ်ခုကို ၃၀ စက္ကန့် စောင့်ပြီး စုစုပေါင်း ၃ ကြိမ် ကြိုးစားပါတယ်။ ၃ ကြိမ်လုံး မရရင် Manual Check လို့ Transaction Log မှာပဲ မှတ်ပါတယ် (RT ထဲမှာ ဘာမှ မပြောင်းပါ)။ Node-RED က ဖြေပေမယ့် rule လိုအပ်တဲ့ job တစ်ခု error ဖြစ်ရင်တော့ (ဥပမာ 2008 — 24 နာရီ usage မရ) ticket ကို NOC၊ In Progress နဲ့ error message comment ထားပါတယ်။

As a NOC engineer, I need a ticket whose CPE data cannot be retrieved to be flagged for Manual Check, so that a data-source failure never causes a wrong automatic resolution or a lost ticket.

  1. AC09Timeout and attemptsCPE data request fail ဖြစ်ရင် ဒါမှမဟုတ် ၃၀ စက္ကန့် ကျော်ရင် စုစုပေါင်း ၃ ကြိမ် ကြိုးစားတယ် (exponential backoff မရှိ)။ Fail ဖြစ်တဲ့ request ကို နောက်မှ ပြန်လုပ်ဖို့ မသိမ်းဘူး။A CPE data request that fails or exceeds 30 seconds is attempted 3 times in total (2 retries) without exponential backoff. The failed request is not saved for later.
  2. AC10Manual Check၃ ကြိမ်လုံး fail ရင် Manual Check လို့ မှတ်ပြီး log လုပ်တယ်။ RT ထဲမှာ (status၊ queue၊ comment) ဘာမှ မပြောင်းဘူး။If all 3 attempts fail, the ticket is flagged Manual Check and the failure is logged. Nothing in RT (status, queue, comment) marks it as Manual Check.
  3. AC11Partial dataNode-RED ဖြေပေမယ့် rule လိုတဲ့ job error ဖြစ်ရင် (ဥပမာ 2008) → NOC၊ In Progress၊ error message ကို comment (SAI Customer Site၊ RCC Customer-ONU)၊ Transaction Log မှာ Manual Check။ Rule မလိုတဲ့ field error တွေကို လျစ်လျူရှုတယ်။When Node-RED answers but a job that the rules need reports an error (for example missing 24 h usage, error 2008), the ticket moves to NOC with status In Progress and the Node-RED error message as the RT comment (SAI Customer Site, RCC Customer-ONU), and is recorded as Manual Check in the Transaction Log. Errors on fields the rules do not need are ignored.
  4. AC46API failure loggedAPI fail၊ timeout ဒါမှမဟုတ် response မမှန်ရင် API name၊ အကြောင်းရင်း၊ detail၊ ရလဒ်ကို မှတ်တယ်။An API failure, timeout or invalid response is recorded with the API name, reason, details and result.
Redmine မူရင်း အသေးစိတ် (Notes, Open points, Implementation status)

PRD: https://rnd.frontiir.net/en/products/rt/requirements/noc-ticket-automation-prd

Notes / dependencies: Depends on the Node-RED API owner (30 s timeout, 3 attempts in total). For this release a Manual Check from a failed call (AC10) has no RT marker and is identified only in the Transaction Log and daily report (S11); a Node-RED job error (AC11) is also marked in RT by the error route. Pending is deferred pending a ticket life-cycle review.

Open points:

  • AC11: Decided 2026-11-19 (PM, Dev, NOC): the Workflow Engine error route (NOC, In Progress, error-message comment) is the Manual Check treatment for a job error; a comment is acceptable because it is the NOC workflow that runs. Only errors on the fields the rules need count. The engine already behaves this way.

S5 OLT၊ PON နဲ့ line-quality ပြဿနာတွေကို NOC ဆီ စစ်တွေ့ချက်နဲ့ ပို့OLT, PON and line-quality faults are routed to NOC with the findings #22953 New 6 AC BaNyar Sithu
ရိုးရှင်းစွာ ပြောရရင်

NOC ကိုယ်တိုင် ကြည့်ရမယ့် network ပြဿနာတွေပါ — OLT offline၊ ONU on/off များတာ၊ port loss၊ BIP8 error (၃ ရက် ပျမ်းမျှ ၂၀ ကျော်)၊ line profile မှားတာ၊ EPC outage (ONU မအလုပ်လုပ်ပြီး နောက်ဆုံးမြင်တာ ၁၂ နာရီအောက်)။ ဒါတွေ တွေ့ရင် ticket ကို NOC ဆီ ပို့ပြီး တွေ့ချက်ကို comment မှာ ရေးပါတယ်။ ဒါမှ NOC engineer က network ကို အစကနေ ပြန်မစစ်ရဘဲ diagnosis ကနေ စလုပ်နိုင်မှာပါ။

As a NOC engineer, I need a ticket with an OLT outage, PON-side error or line-profile problem routed to NOC with the findings in the comment, so that I start from the diagnosis instead of re-checking the network.

  1. AC12OLT offlineOLT offline ဆိုရင် OLT-offline field၊ status နဲ့ comment ထည့်ပြီး NOC ဆီ ရွှေ့တယ်။When the OLT is offline the ticket moves to NOC with the OLT-offline fields, status and comment.
  2. AC15ONU on/offONU on/off အကြိမ်ရေ ၃ ရက် ပျမ်းမျှ ၂၀ ကျော်ရင် NOC ဆီ ရွှေ့တယ်။When the 3-day average ONU on/off count exceeds 20 the ticket moves to NOC with the matching fields and comment.
  3. AC16Port lossPort loss ၃ ရက် ပျမ်းမျှ ၂၀ ကျော်ရင် NOC ဆီ ရွှေ့တယ်။When the 3-day average port-loss count exceeds 20 the ticket moves to NOC with the matching fields and comment.
