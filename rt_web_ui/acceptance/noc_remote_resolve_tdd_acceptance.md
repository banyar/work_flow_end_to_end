# NOC Remote Resolve Automation
## Test-driven acceptance specification

Use this document as the acceptance contract for the API, Kafka publisher, `rtutil`, RT integration, Peppermint integration, sweepers, and NOC reporting. Each case gives the condition to create, the event to trigger, and the observable result. Implement the tests in the existing repositories and run them against the release candidate.

Basis: the six findings in `noc_automation_flow_review/index.html`, the companion sweeper notes, and the separate v2 admission and Redis proposal. The review package contains documentation and reported test results. This specification has not been executed against the application.

### Release profiles

| Profile | Scope |
|---|---|
| **P · Supervised pilot** | Required for the current release in a defined pilot scope. The release may hand off recoverable failures to NOC, with an assigned owner and response target. |
| **U · Unattended rollout** | Required in addition to P before enabling unattended recovery or claiming unattended production readiness. |
| **V · v2 admission and Redis** | Required if the v2 proposal ships. Run alongside the applicable P and U tests. |

The OSS owner, NOC owner, and engineer should agree on the following behavior before using the cases as a release gate. Put the approved values and profiles in version control.

| Decision | Proposed acceptance contract |
|---|---|
| Uncertain external action | Show **Needs reconciliation** with the affected action, ticket/run reference, known job or operation ID, and time. A timeout alone leaves the action outcome unknown. Authoritative evidence can resolve it later. A manual handoff stays visible until disposition is recorded. |
| Ownership during handoff | An old action cannot overwrite a newer operator change. Use an atomic downstream precondition or equivalent protection where supported. When a dispatched action cannot be fenced or cancelled, explicitly track it and prevent conflicting re-execution. NOC must see that action as outstanding and reconcile it before a conflicting change. If the downstream system cannot support a safe handoff for an action, keep that action out of the pilot scope. |
| Ticket and service outcomes | Track RT update, BCS outcome, and service verification independently. If BCS is required for a ticket's remedy, keep the ticket out of any verified-resolution state until required actions succeed and recovery is verified. For the pilot, a NOC operator can record the verification. Agree which RT statuses and queues express each outcome. |
| Admission identity | Use a stable identifier for a single admission attempt across retries, or an equivalent lookup that returns its authoritative disposition. A separate ticket revision or authorized rerun may represent a new intent. Keep the active-run constraint and the 24-hour suppression policy as separate rules. Agree which terminal states count and how approved overrides work. For v2, the proposal excludes `NOT_ELIGIBLE` from the cooldown. |
| Runtime settings | Test the actual release configuration. The response describes a five-minute API sweep threshold, a ten-minute `rtutil` stuck threshold, and BCS polling/give-up targets at five/ten minutes. Verify which settings are active, their start events, and the boundary rule at the exact cutoff. If the current pilot retains `updated_at` for API timeouts, document the write invariant it depends on. Time BCS polling from job acceptance, independently of later RT updates. |
| Outage and NOC response targets | Agree on peak ticket arrivals, a representative eligible backlog, allowable downstream concurrency, time to surface a handoff, and time for NOC to acknowledge it. Use 300 eligible runs as a reproducible starting workload and add a mixed-state outage. Record the observed latency and backlog against the agreed targets. |
| v2 admission disposition | A successfully admitted request has a durable run. A duplicate or suppressed request has an explicit disposition, including the existing run reference where applicable. Record uncertainty when the API may have accepted a request. Import failures independently of CSV export. |

### Test environment and evidence

- **Unit** tests cover policy, transitions, reporting mappings, and deadline boundaries. Use a controllable clock.
- **Integration** tests use the deployed MariaDB schema and migration path, real Kafka producer and consumer-group behavior, and real Redis for v2. Use RT and Peppermint simulators that store accepted operations independently of the worker. Test the production adapter contracts in a safe staging environment for downstream deduplication, lookup, conditional update, and callback behavior.
- **Fault tests** kill or restart the actual worker at named checkpoints. A timeout-after-acceptance simulation must first persist the external action, then withhold the response. Use synchronization barriers to force races and controlled clocks for time-based cases. Use a separate end-to-end check with real timers for the release settings.
- **Evidence** for each applicable case includes the test ID, release commit, configuration, command, and pass/fail result. For critical cases capture the run timeline, downstream accepted operations and actual effects, final RT queue/status/comments, Kafka offset where relevant, and the NOC-visible disposition. Count HTTP attempts separately from applied effects.
- **Shared fixtures** include an eligible NOC ticket requiring BCS, an eligible ticket that does not require BCS, one fixture per eligibility rejection, a reopened ticket, a ticket moved by NOC, and two tickets sharing a Kafka partition. Use a stable request ID, `run_id`, ticket revision or equivalent precondition, and BCS job ID as applicable.
- **Core assertions** apply wherever relevant. Each accepted request remains discoverable. A ticket has at most one active run. Terminal execution state never regresses. An operation has at most one applied effect per logical action. External actions cannot overwrite a newer operator decision. RT completion, BCS confirmation, and verified service recovery remain independently observable.

### 2. MariaDB, Kafka, and restart recovery

| ID | Gate / level | Given and when | Expected result |
|---|---|---|---|
| PUB-01 | P / fault | Fail the transaction that saves the evaluated payload or its event, immediately before publish. | No Kafka publish or downstream action occurs. The run follows the configured recovery path with a discoverable reason. |
| PUB-02 | P / fault | With the relay disabled, kill the API after committing the evaluated payload and before calling Kafka. | The payload and run remain queryable. No Kafka message exists for the run. The configured sweep produces one actionable NOC handoff without an automatic resend. |
| PUB-03 | P / fault | Kill the API after Kafka accepts the result and before `PUBLISHED` is recorded. Start the consumer while the run is still `WORKFLOW_EVALUATED`. | The consumer can claim and process the valid run once if it is still active. The final database state, RT result, and audit trail agree. |
| PUB-04 | P / integration | Delay the producer's `PUBLISHED` state write until the consumer is in each of `CONSUMED`, `RT_UPDATING`, and `COMPLETED`. | The late producer write leaves the advanced state intact and emits no false transition. |
| PUB-05 | P / integration | Let the sweeper close the run first, then deliver the delayed Kafka message or producer completion. | The message and late state write cannot reopen the run. The consumer produces zero RT or BCS effects and records a traceable stale-message disposition. |
| PUB-06 | P / fault | Kafka accepts the publish but the producer receives a timeout or loses its acknowledgment. Deliver any copies that exist. | Applied effects remain single. The run reflects successful consumer processing or an actionable uncertain outcome, consistent with observed evidence. |
| PUB-07 | U / fault | With automatic recovery enabled, repeat PUB-02 and restart the publisher. | Persisted work is discovered and sent by the recovery process. The ticket completes within the agreed recovery target or reaches a bounded, explicit handoff. |
| PUB-08 | U / fault | Kill the relay after Kafka accepts a publish and before relay progress is saved. Restart it and allow duplicate messages. | Durable work eventually reaches the consumer. Duplicate delivery cannot repeat either downstream action. |
| PUB-09 | U / integration | Kafka is unavailable across several attempts, then recovers. Also test an outage longer than the configured retry budget. | Work resumes after recovery within budget. Exhaustion records a reason and a single handoff. Attempt rate, concurrency, and outstanding age remain bounded. |
| RCV-01 | P / fault | Kill the API separately in `RECEIVED`, `FETCHING_CPE_STATUS`, `WORKFLOW_EVALUATED`, and `PUBLISHED` before consumer claim. | For each state, the release matrix leads to a completed run or visible handoff within its configured recovery policy. Assertions distinguish unpublished work from a published result awaiting consumption. |
| RCV-02 | P / fault | Kill `rtutil` separately after entering `CONSUMED`, `BCS_UPDATING`, and `RT_UPDATING`, before the next durable step. | Kafka redelivers or a durable worker resumes from the saved phase. Completed effects are preserved, remaining work finishes, and checkpoints and events agree. |
| RCV-03 | P / fault | Complete and durably record the run, then crash before committing the Kafka offset. | The duplicate message is consumed and safely acknowledged. No new BCS, RT, or comment effect occurs. |
| RCV-04 | P / fault | Two messages share one partition. Hold the earlier message before its outcome is durable, finish the later one, and crash or rebalance the group. | Offset progress does not strand the earlier message. Both runs remain recoverable with no lost effects or duplicates. |
| RCV-05 | P / integration | Run the release image with the deployed stuck-timeout setting. Stall each consumer state just below, at, and above its cutoff. | The behavior matches the signed configuration, including which states are monitored. A healthy worker making permitted progress can finish. A stalled run is reconciled or surfaced to NOC within the agreed interval. |
| RCV-06 | P / integration | Upgrade with active runs in each supported intermediate state, an older Kafka payload, and older checkpoints. Restart the services. | In-progress work resumes or reaches an explicit migration/handoff disposition. Existing outcomes, correlation IDs, and deduplication protections survive the deployment. |
| RCV-07 | P / integration | Force an event insert to fail while a state transition is in progress, then retry the transition. | State and event both roll back or both commit. The successful transition has one matching audit event and the terminal state cannot move backward. |

### 3. BCS and RT action boundaries

| ID | Gate / level | Given and when | Expected result |
|---|---|---|---|
| ACT-01 | P / contract + fault | **Peppermint accepts a job and loses the reply.** Restart `rtutil`, then retry or reconcile with the original operation identity. | Peppermint shows one accepted job and one applied change. | ACT-02 | P / fault | Persist the BCS job reference and crash before the next RT step. | Restart uses the existing job reference and proceeds through the remaining permitted RT steps. No second BCS job is accepted. |
| ACT-03 | P / contract | Retry a Peppermint request concurrently and near the end of its deduplication retention. | ACT-04 | P / fault | **RT applies the intended status/queue change and the worker crashes before the comment is written or the status checkpoint is saved.** | Resume recognizes the existing update, finishes any still-valid comment exactly once, and records the completed steps. | ACT-05 | P / fault | RT persists the automation comment and then loses the reply. Crash before the comment checkpoint. | Resume finds the comment for this operation and leaves exactly one copy. It reaches a durable completion or reconciliation disposition. |
| ACT-06 | P / fault | Two `rtutil` workers receive copies of the same message and reach the comment check concurrently. | Both workers cannot append the same logical comment. | ACT-07 | P / integration | Move the ticket out of NOC before `rtutil` checks it. | ACT-08 | P / contract + fault | Change the ticket after `rtutil` reads it and before its RT write takes effect. | The downstream precondition or equivalent serialization preserves the newer operator change. | ACT-09 | P / integration | Return a confirmed BCS rejection, a confirmed RT rejection, a timeout after RT accepts, and a timeout before RT accepts. | ACT-10 | P / integration | Send unrelated ticket comments that resemble the automation marker, and send two distinct valid runs on the same ticket under the reprocessing policy. | The marker identifies the specific operation. | ACT-11 | P / integration | Deliver a duplicate event after the original run is terminal. Repeat with a later run for the same ticket already active. | The old event produces zero new RT/BCS effects and leaves the later run unchanged. |

### 4. Timeout, stale work, and NOC handoff

| ID | Gate / level | Given and when | Expected result |
|---|---|---|---|
| STALE-01 | P / fault | Pause a worker before its final action guard. Let the sweeper close the run, then release the worker. Repeat for publish, BCS submit, RT update and comment. | A stale worker cannot initiate those actions. The terminal state remains intact and no false completion is recorded. |
| STALE-02 | P / fault | Pause a worker after its last local check but before the request takes effect. Let the sweeper run and have NOC take over. | STALE-03 | P / contract + fault | **RT or Peppermint accepts the request, the response is delayed past timeout, and a NOC operator takes over before the original request finishes.** Execute once per downstream system. | An already-issued operation cannot overwrite a newer authorized change. If fencing is unavailable, NOC can see and reconcile the outstanding action before making a conflicting change. Late success/failure updates the action evidence without resurrecting the closed workflow. |
| STALE-04 | P / integration | Race the sweeper and an active worker on the same candidate after selection. Repeat with two sweepers racing to close it. | An atomic recheck makes the outcome consistent. A run that has advanced beyond the selected state is left alone. A timed-out run gets one terminal transition and one handoff. |
| STALE-05 | P / integration | Let a timed-out attempt become eligible for manual rerun or cooldown expiry while an old message and an unknown action remain. | The old message has zero effects. Reprocessing observes the outstanding action and the approved override policy. Resolution of that action is traceable before a conflicting operation can proceed. |
| STALE-06 | P / integration + NOC exercise | Simulate an unresolved RT or BCS action through the real report/alert path and have the responsible NOC operator respond. | The case reaches the assigned queue within the agreed time, has the ticket/run/action references and last known evidence, and remains open until the operator records disposition. Repeated sweeps do not create duplicate handoffs. |
| STALE-07 | U / contract + fault | Repeat STALE-02 and STALE-03 during automated recovery, including an old worker that resumes after ownership has transferred. | Downstream effects honor current ownership or revision. ### How to use the specification with AI-assisted coding

1. Have the OSS owner approve the observable outcomes and NOC operating policy. The engineer maps every applicable ID to named tests and flags unsupported downstream contracts with evidence.
2. For each change, write the failure case first. Capture the failing assertion against the old behavior, make the change, and run the case again. For already-implemented safeguards, temporarily disable the specific safeguard in a disposable test build and confirm that the targeted test fails.
3. Keep simulator assertions independent of implementation logic. Inspect the external system's stored effects, Kafka offsets, database state, and operator-visible output. A mocked success response or a final `COMPLETED` row alone is insufficient evidence.
4. Put deterministic cases in CI. Run real-dependency fault tests and release configuration checks before promotion. Keep the load run and NOC handoff exercise as recorded staging evidence. Treat a skipped required case or an unverified downstream contract as an explicit sign-off item.
5. Review changes to expected outcomes as product and architecture decisions. Require an independent reviewer for critical tests and code changes. Keep the original failing case, passing evidence, and agreed release profile together.

For pilot sign-off, review **ACT-01**, **ACT-04**, and **STALE-03** first, then verify the complete P suite and the NOC handoff exercise. Record unresolved trade-offs against the release profile and its scope.
