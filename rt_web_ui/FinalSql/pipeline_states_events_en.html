Pipeline State Reference

Every state a remote-resolve pipeline run can pass through, and every event written to pipeline_run_events, collected straight from the code (rt_web_ui, noc_automation, rtutil, rtdatacore). Use it when reading the database tables or finding where a run is stuck.

How the three tables relate

pipeline_runs

One row per run. current_state says where the run is now, last_state_reason why, and completed_at when it reached a terminal state.

pipeline_run_events

Append-only history. One row per state change (from_state → to_state) and per step that does not change the state (from_state = to_state): how the run got there.

retry_jobs

A job the Retry Worker runs later when the Node-RED fetch or the Kafka publish fails. The job being retried is linked from pipeline_runs.active_retry_job_id.

All three tables are joined on run_id (a UUID, CHAR(36)). There is no foreign key; the applications keep the reference consistent.

State flow

The normal path runs left to right; a failure stops the run in a terminal state. PUBLISHED is not terminal: the decision has reached Kafka and rtutil still has to pick it up, so completed_at stays empty.

ColumnValueMeaning
statusPENDINGWaiting for next_retry_at

statusRESOLVEDThe retry succeeded (resolved_at)
statusFAILED_PERMANENTNo attempts left (attempt_count = max_attempts) or an error a retry cannot fix
job_typeNODE_RED_FETCHRepeats the Node-RED CPE status fetch (the whole pipeline replays from there)
