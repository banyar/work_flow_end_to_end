Concurrent Ticket Submission Handling

2026-10-18 · Remote-resolve pipeline · Design (implementation မလုပ်ရသေး)

Ticket တစ်စောင်တည်းကို tab များများ၊ user နှစ်ယောက်၊ API တိုက်ရိုက်ခေါ်တာ ဘယ်လိုပဲ ပြိုင်တူ ပို့ပို့ database ရဲ့ unique index က တစ်ခုပဲ လက်ခံပြီး ကျန်တာကို ပယ်ပါမယ်။ DB အတွင်းမှာ InnoDB row lock နဲ့ လုပ်တာဖြစ်လို့ application ဘက်မှာ lock code ရေးစရာ မလိုပါ။

အကြံပြုချက်အနှစ်ချုပ်: နည်းငါးမျိုး နှိုင်းယှဉ်ပြီး Section 12 မှာ DB unique index + lazy takeover ကို အကြံပြုထားပြီး Section 13 မှာ အသေးစိတ် plan ရှိပါတယ်။

2. ဖြေရှင်းနည်း: active run unique index

Ticket တစ်စောင်မှာ မပြီးသေးတဲ့ run (completed_at IS NULL) တစ်ခုပဲ ရှိခွင့်ပြုတဲ့ index ကို pipeline_runs မှာ ထည့်ပါမယ်။

ALTER TABLE pipeline_runs
  ADD active_ticket_id bigint(20) unsigned
      AS (IF(completed_at IS NULL, ticket_id, NULL)) PERSISTENT,
  ADD UNIQUE KEY uq_pipeline_runs_active_ticket (active_ticket_id);
  • Run မပြီးသေးရင် active_ticket_id = ticket_id ဖြစ်လို့ ticket တူ run နောက်တစ်ခု insert လုပ်ရင် duplicate error ဖြစ်ပါတယ်။
  • Run ပြီးသွားရင် (completed_at ဖြည့်) active_ticket_id = NULL ဖြစ်ပါတယ်။ Unique index က NULL တွေကို ကန့်သတ်မထားလို့ နောက်ထပ် run ဖွင့်ခွင့် ပြန်ရပါတယ်။
  • Request ဘယ်ကလာလာ pipeline run ဖွင့်ဖို့ ဒီ table ထဲ insert လုပ်ရပါတယ်။ ဒါကြောင့် DB တစ်နေရာက အားလုံးကို တားပါတယ်။

ဘာကြောင့် UNIQUE (ticket_id) တိုက်ရိုက် မထည့်တာလဲ: အဲဒါဆိုရင် ticket တစ်ခုမှာ run တစ်ခါပဲ ရှိခွင့်ရလို့ နောက်နေ့ ticket ပြန်ဖွင့်လာရင်တောင် run အသစ် မဖွင့်နိုင်ပါ။ တားချင်တာက "တစ်ပြိုင်နက်" ကိုပဲ ဖြစ်လို့ မပြီးသေးတဲ့ run တွေကိုပဲ ရွေးတားဖို့ generated column လိုပါတယ်။

Implement လုပ်တဲ့အခါ သတိထားရန်

  1. ALTER မလုပ်ခင် duplicate ရှိမရှိ စစ်ပါ။ ticket တူ မပြီးသေးတဲ့ run နှစ်ခု ရှိနေရင် ALTER ကိုယ်တိုင် 1062 နဲ့ fail ပါမယ်။ ရလဒ်ပါလာရင် run ဟောင်းတွေကို (Section 8 runbook SQL နဲ့) အရင်ပိတ်ပါ: 
    SELECT ticket_id, COUNT(*) FROM pipeline_runs
 WHERE completed_at IS NULL AND ticket_id IS NOT NULL
 GROUP BY ticket_id HAVING COUNT(*) > 1;
  2. App က ဒီ column ကို မရေးရပါ။ Generated column ထဲ value ထည့်ရင် MariaDB က error 1906 (strict mode) ပြပါတယ်။ rtdatacore entity မှာ GORM tag ကို read-only (gorm:"->") ထားရပါမယ်၊ မဟုတ်ရင် GORM က insert ထဲ ထည့်ပါမယ်။
  3. ALTER က table ကို rebuild လုပ်ပါတယ်။ Row တိုင်းအတွက် တွက်ရလို့ table ကြီးရင် အချိန်ယူပြီး ရေးခွင့်ကို ခဏ ပိတ်နိုင်ပါတယ်။ Release window မှာ run ပါ။
  4. completed_at ကို terminal state တိုင်းမှာ ဖြည့်ရပါမယ်။ ဒီစည်းကမ်းက completed_at ကိုပဲ ကြည့်လို့ terminal ရောက်ပြီး မဖြည့်မိရင် ticket ပိတ်နေပါမယ်။ လက်ရှိ rtdatacore က terminal state မှာ ဖြည့်ပေးပါတယ်။
  5. ticket_id NULL ဆိုရင် မတားပါ။ Gate မှာ ticket_id အမြဲပါလို့ ပြဿနာ မရှိပါ။

6. သတိထားရမယ့်အချက်များ

  1. Insert ကို transaction တိုတိုနဲ့ ထားပါ။ Insert နဲ့ HTTP call (Node-RED စသည်) ကို transaction တစ်ခုတည်းထဲ ထည့်ရင် ကျန်တဲ့ click တွေက HTTP call ပြီးတဲ့အထိ စောင့်နေရပါမယ်။ Insert ကို autocommit လုပ်ပြီးမှ ကျန်အလုပ်တွေ လုပ်ပါ။
  2. Stuck run က ticket ကို ပိတ်ထားနိုင်ပါတယ်။ Run က terminal state မရောက်ရင် completed_at NULL ပဲ ကျန်ပြီး ticket ကို ထပ်မ run နိုင်တော့ပါ။ Stuck sweeper (PUBLISHED_TIMEOUT_ENABLED၊ လက်ရှိ false) ဖွင့်ထားရမယ်၊ သို့မဟုတ် admin က manual ပိတ်ပေးနိုင်တဲ့ နည်း ရှိရပါမယ်။
  3. Run ပြီးရင် ထပ်နှိပ်ခွင့်ရပါတယ်။ ဒီ index က "တစ်ပြိုင်နက်" ကိုပဲ တားပါတယ်။ ပြီးသွားတဲ့ ticket ကို ထပ်တားချင်ရင် ALREADY_PROCESSED (၂၄ နာရီ rule) ဆိုတဲ့ business rule သီးသန့် လိုပါတယ်။
  4. ticket_id NULL ဆိုရင် unique က မတားပါ။ ticket_id က gate မှာ အမြဲ ပါပြီးသားမို့ ပြဿနာ မရှိပါ။
  5. အရင်ဆုံး insert လုပ်တဲ့နေရာ က RT Web UI ဘက်ဖြစ်လို့ duplicate error ကို အဲဒီမှာ ကိုင်တွယ်ရပါမယ်။

7. Production: RT Web UI cluster ၅ လုံး

Production မှာ RT Web UI ကိုပဲ instance ၅ ခု run ထားပြီး RT database (rt5) ကို ၅ ခုလုံး မျှသုံးပါတယ်။ ဒါကြောင့် unique index နည်းက ပြောင်းစရာ မလိုဘဲ အလုပ်လုပ်ပါတယ်။ Lock ယူတာက RT Web UI node မှာ မဟုတ်ဘဲ DB မှာ ဖြစ်လို့ node ဘယ်နှခု ရှိရှိ အတူတူပါပဲ။

RT Web UI ဘက်မှာ လုပ်ရမှာ:

  1. Run row insert မှာ duplicate ကို ကိုင်တွယ်ပါ။ RT Web UI (Perl / DBI) က insert လုပ်တဲ့အခါ error 1062 ရရင် noc API ကို မခေါ်ဘဲ "Ticket is already being processed" ပြပါ (Section 5)။ Node ၅ ခုလုံးမှာ code တူတူ deploy ဖြစ်ရပါမယ်။
  2. Insert ကို autocommit နဲ့ ချက်ချင်း commit လုပ်ပါ။ RT request ရဲ့ transaction ကြီးထဲ ထည့်ရင် lock ကို request ပြီးတဲ့အထိ ကိုင်ထားပြီး ကျန် node တွေ စောင့်နေရပါမယ်။
  3. DB primary ကိုပဲ ရေးပါ။ RT DB မှာ read replica ရှိရင် node တွေက insert ကို primary ကို ပို့ရပါမယ်။

Node တစ်ခု သေရင် (restart / deploy): Node က run row ကို insert ပြီး noc API မခေါ်ရသေးခင် သေရင် run က state "" မှာ ကျန်ပြီး ticket ကို ပိတ်ထားပါမယ်။ noc_automation restart ဖြစ်ရင်လည်း SUBMITTED_TO_API / RECEIVED မှာ ကျန်နိုင်ပါတယ်။ ဒါကြောင့်:

  • Terminal မဟုတ်တဲ့ state အားလုံး (""၊ SUBMITTED_TO_API၊ RECEIVED၊ PUBLISHED …) ကို N မိနစ်ကျော်ရင် terminal (ဥပမာ FAILED_PERMANENT) ပြောင်းပြီး completed_at ဖြည့်ပေးတဲ့ sweeper လိုပါတယ်။ လက်ရှိ PUBLISHED အတွက်ပဲ ရှိပြီး ပိတ်ထားပါတယ် (PUBLISHED_TIMEOUT_ENABLED=false)။
  • Sweeper ကို noc_automation (instance တစ်ခု) မှာ ထားရင် node ၅ ခုကြား ညှိစရာ မလိုပါ။ UPDATE … WHERE current_state = ? AND updated_at < ? ပုံစံ conditional update နဲ့ ပိတ်ရင် RT Web UI က အချိန်တူ ရေးနေတာနဲ့ မတိုက်ပါ။

နောက်ဘက် service တွေ: noc_automation နဲ့ rtutil က instance တစ်ခုစီပဲ ဖြစ်ပြီး run အောင်တဲ့ တစ်ခုပဲ သူတို့ဆီ ရောက်တော့ Node-RED၊ Kafka၊ RT update၊ BCS တစ်ခါပဲ ဖြစ်ပါတယ်။ နောင် သူတို့ကို scale out လုပ်လည်း entry guard က အရင်တားပြီးသား ဖြစ်ပါတယ်။

အတည်ပြုရန်: RT DB က server တစ်ခုတည်း (သို့ primary + replica) ဖြစ်ရပါမယ်။ RT DB ကိုယ်တိုင် Galera multi-master ဆိုရင် node မတူတဲ့ insert ရှုံးတာက 1062 မဟုတ်ဘဲ 1213 Deadlock ရလို့ အဲဒါကိုပါ ကိုင်တွယ်ရပြီး staging မှာ ပြန်စမ်းရပါမယ်။

8. Release မှာ sweeper ပိတ်ထားရင်

Background sweeper မရှိရင် stuck run တစ်ခုက ticket ကို အမြဲ ပိတ်ထားပါမယ်။ ဖြေရှင်းနည်းက insert မှာ duplicate ရတဲ့အခိုက် ရှိနေတဲ့ run ဟောင်းနေရင် အဲဒီမှာပဲ ပိတ်ပြီး ပြန် insert လုပ်တာ (lazy takeover) ပါ။ Sweeper မလိုဘဲ ticket ကို တစ်ယောက်ယောက် ထပ်နှိပ်မှသာ စစ်ပါတယ်။

1. INSERT run                                   → အောင် → noc API ခေါ် (ပုံမှန်)
2. 1062 ရ → ရှိနေတဲ့ active run ကို ဖတ်
     SELECT run_id, current_state, updated_at
       FROM pipeline_runs WHERE active_ticket_id = :ticket_id
3. updated_at က cutoff ထက် နောက်ကျ (အသက်ရှင်) → "Ticket is already being processed" (ရပ်)
4. updated_at က cutoff ထက် စော (ဟောင်း/stuck) → conditional UPDATE နဲ့ ပိတ်
     UPDATE pipeline_runs
        SET current_state = 'FAILED_PERMANENT',
            last_state_reason = 'stale run closed: ticket resubmitted',
            completed_at = :now, updated_at = :now
      WHERE run_id = :old_run_id
        AND completed_at IS NULL
        AND updated_at < :cutoff
     + pipeline_run_events ထဲ event တစ်ကြောင်း (audit)
5. INSERT ကို တစ်ခါပဲ ပြန်စမ်း → အောင် → ဆက်လုပ် / 1062 → "already being processed"

ပြိုင်တူ ၅ ခါ နှိပ်ရင်လည်း မှန်ပါတယ်: ၅ ခုလုံး 1062 ရပြီး ၅ ခုလုံး UPDATE လုပ်ပါတယ်။ Row lock ကြောင့် ပထမ UPDATE က 1 row ပြောင်းပြီး ကျန် ၄ ခုက completed_at IS NULL မမှန်တော့လို့ 0 rows ပါ။ ပြီးရင် ၅ ခုလုံး ပြန် INSERT လုပ်တော့ unique index က တစ်ခုပဲ လက်ခံပါတယ်။ RT Web UI node ၅ ခုကြားမှာ ညှိစရာ မလိုပါ။

Ticket အလိုက် Redis key ကို 24 နာရီ TTL နဲ့ ထားရင် အဓိကပြဿနာက "တစ်ပြိုင်နက် ပို့တာ တားတာ" နဲ့ "24 နာရီအတွင်း ထပ်လုပ်တာ တားတာ" ဆိုတဲ့ ရည်ရွယ်ချက် ၂ ခုကို key တစ်ခုထဲ ရောထည့်မိတာပါ။ Concurrency က စက္ကန့်ပိုင်းပဲ ကြာပေမယ့် key က 24 နာရီ ပိတ်ထားလို့ တကယ် ထပ်လုပ်ရမယ့် case တွေပါ ပိတ်ခံရပါတယ်။

Idempotency key ဆိုတာ: run_id ကို random UUID အစား ticket ကနေ တွက်ထုတ်တာ (ဥပမာ UUIDv5(ticket_id + LastUpdated))။ Click ၅ ခါလုံး run_id တူထွက်လို့ ရှိပြီးသား run_id unique နဲ့ 409 က ပယ်ပေးပါတယ်။

1. Ticket re-open flow နဲ့ တိုက်ပါတယ် (အကြီးဆုံး)

  • RT Web UI gate က re-open, re-open-1 … re-open-5 status တွေကို ခွင့်ပြုထားပြီး rtutil က ReOpen → Resolved2၊ ReOpen2 → Resolved3 … ပြောင်းပေးပါတယ်။ Ticket ပြန်ဖွင့်ပြီး ထပ် process လုပ်တာ design ထဲမှာ ပါပြီးသား ဖြစ်ပါတယ်။

10. Idempotency key: run_id ကို ticket ကနေ တွက်ထုတ်ခြင်း

Idempotency key ဆိုတာ "input တူရင် ID တူ ထွက်တာ" ပါ။ run_id ကို random မထုတ်ဘဲ ticket ရဲ့ အခြေအနေကနေ တွက်ထုတ်ရင် ပြိုင်တူ ပို့တဲ့ request တွေက run_id တူ ရပြီး DB ရဲ့ ရှိပြီးသား run_id unique index က တစ်ခုပဲ လက်ခံပါတယ်။ Schema မပြောင်းရတာ အားသာချက်ပါ။ ဒါပေမဲ့ ticket ပြောင်းသွားရင် ID ပါ ပြောင်းလို့ DB unique index (Section 2) လောက် မခိုင်ပါ။

လက်ရှိ ဘယ်လိုလဲ

RT Web UI က နှိပ်တိုင်း random UUID ထုတ်ပါတယ်။ ငါးခါနှိပ်ရင် run_id ငါးမျိုး ထွက်ပြီး DB က "run ငါးခု မတူဘူး" လို့ ထင်လို့ ငါးခုလုံး လက်ခံပါတယ်။

Idempotency key နဲ့ဆိုရင်

run_id = UUIDv5(namespace, "<ticket_id>:<ticket ရဲ့ နောက်ဆုံး transaction id>")
  • UUIDv5 က namespace နဲ့ စာသားကို hash (SHA-1) လုပ်ပြီး UUID ပုံစံ ထုတ်ပေးပါတယ်။ Random မပါလို့ input တူရင် အမြဲ output တူ ပါတယ်။ ဘယ် server၊ ဘယ်အချိန်မှာ တွက်တွက် အတူတူပါပဲ။
  • namespace က system အတွက် သတ်မှတ်ထားတဲ့ UUID ကိန်းသေ တစ်ခုပါ။ RT Web UI node ငါးခုလုံး တူတူ သုံးရပါမယ်။

11. noc_automation မှာ mutex + DB စစ်ခြင်း

ပြိုင်တူ request တွေကို noc_automation မှာ တစ်ခုချင်း တန်းစီ (mutex) ပြီး "ဒီ ticket ကို တခြား run က ယူထားပြီးလား" ဆိုတာ DB မှာ စစ်တဲ့ နည်းပါ။ noc က instance တစ်ခုတည်း ဖြစ်နေသရွေ့ ငါးခုထဲက တစ်ခုပဲ ဆက်လုပ်ပြီး ကျန်တာ 409 ရပါတယ်။ Schema မပြောင်းရပါ။ ဒါပေမဲ့ noc ကို တစ်ခုထက်ပို run တာနဲ့ (deploy လုပ်နေတဲ့ ခဏလည်း အပါအဝင်) ပျက်ပါတယ်။

Mutex ကိုင်ထားချိန်က DB query ၂ ကြောင်းစာပဲ (millisecond) ဖြစ်ပါတယ်။ Node-RED ခေါ်တာက mutex အပြင်မှာမို့ request တွေ အကြာကြီး မစောင့်ရပါ။

"မပြီးသေးတဲ့ run" ကို ဘယ်လို စစ်မလဲ (အရေးကြီးဆုံး)

completed_at IS NULL လို့ ရိုးရိုး စစ်ရင် မှားပါတယ်။ Request 1 ဝင်တဲ့အချိန် ကျန် ၄ ခုရဲ့ row တွေကလည်း SUBMITTED_TO_API (မပြီးသေး) ဖြစ်နေလို့ Request 1 ကိုယ်တိုင်လည်း "ရှိပြီ" လို့ ထင်ပြီး ငါးခုလုံး 409 ဖြစ်ပါမယ်။ ဒါကြောင့် noc က ယူပြီးသား (claimed) run ကိုပဲ ရေတွက်ရပါတယ်:

SELECT run_id FROM pipeline_runs
 WHERE ticket_id = ?
   AND completed_at IS NULL
   AND current_state NOT IN ('', 'SUBMITTED_TO_API')   -- noc မယူရသေးတဲ့ row မပါ
   AND updated_at > :stale_cutoff                       -- stuck run မပါ (ဥပမာ 30 မိနစ်)
 LIMIT 1;
  • RECEIVED, PUBLISHED, RETRY_SCHEDULED, CONSUMED, BCS_UPDATING, RT_UPDATING ဆိုတာ noc ယူထားပြီး အလုပ်လုပ်နေဆဲ run တွေပါ။ ဒါတွေ ရှိရင် ငြင်းပါ။
  • Stuck run: noc restart ဖြစ်ရင် background goroutine ပျောက်ပြီး run က RECEIVED မှာ ကျန်ပါတယ်။ updated_at cutoff မထားရင် ticket ကို အမြဲ ပိတ်ထားပါမယ်။ Cutoff ကျော်ရင် စစ်ချက်ထဲ မပါလို့ run အသစ် ခွင့်ရပါတယ် (run ဟောင်းကတော့ report မှာ Stuck အဖြစ် ကျန်)။
  • idx_pipeline_runs_ticket_id index ရှိပြီးသားမို့ query မြန်ပါတယ်။ :stale_cutoff ကို app ဘက်က local time နဲ့ ပို့ပါ (NOW() UTC ပြဿနာ)။
  • Mutex ပုံစံ: ticket တိုင်းအတွက် mutex သီးသန့် (map[ticketID]*sync.Mutex) ထားလို့ရပေမယ့် map ကို ပြန်ရှင်းရပါတယ်။ Request နည်းပြီး ကိုင်ချိန် millisecond ပဲမို့ global mutex တစ်ခုတည်း နဲ့ လုံလောက်ပါတယ်။

အားသာချက်

  • Schema မပြောင်းရ၊ ပြင်ရတာ noc တစ်နေရာတည်း (controller + query တစ်ခု)။
  • RT Web UI မဖြတ်ဘဲ API ကို တိုက်ရိုက်ခေါ်တာကိုလည်း တားပါတယ် (noc ကို ဖြတ်ရလို့)။
  • RT Web UI (node ၅ ခု) ကို မပြင်ရပါ (409 message ပြင်ချင်ရင်ပဲ)။

အားနည်းချက်

  1. noc instance ၂ ခု ဖြစ်တာနဲ့ ပျက်ပါတယ်။ Instance တစ်ခုချင်းမှာ mutex သီးသန့် ရှိလို့ ၂ ခုလုံး တစ်ပြိုင်နက် စစ်ပြီး "မရှိဘူး" လို့ ထင်ကာ ယူမိပါမယ်။
    • Deploy လုပ်နေတဲ့ ခဏလည်း ဖြစ်နိုင်ပါတယ်: Kubernetes RollingUpdate က pod အသစ် တက်ပြီးမှ pod ဟောင်းကို ပိတ်လို့ ခဏတာ instance ၂ ခု run နေပါတယ်။ ဒီနည်းသုံးရင် deployment strategy ကို Recreate ထားရပါမယ် (deploy ချိန် စက္ကန့်ပိုင်း downtime ရှိ)။
    • နောင် noc ကို scale out လုပ်ရင် ဒီနည်းကို ဖြုတ်ပြီး DB unique index ကို ပြောင်းရပါမယ်။
  2. Row အပိုနဲ့ report ရှုပ်ပါတယ်: row ၅ ကြောင်း ကျန်ပြီး "API error 409" ၄ ခုက တကယ့် error လို ပေါ်ပါတယ်။
  3. Stuck run: cutoff (30 မိနစ်) မကျော်မချင်း ticket ပိတ်နေပါတယ်။

ဒီ release မှာ schema လုံးဝ မပြောင်းရဘူးဆိုရင် (fallback): noc mutex + DB စစ် (Section 11) ကို ယာယီ သုံးပါ။ noc တစ်နေရာတည်း ပြင်ရပေမယ့် noc deployment ကို Recreate ထားရပြီး report မှာ "API error 409" row တွေ ပေါ်ပါမယ်။ နောက် release မှာ unique index ပြောင်းပါ။

မရွေးသင့်တာ: Idempotency key (ticket ပြောင်းတုန်း duplicate၊ click ကိုယ်တိုင် ticket ရေးရင် guard ပျက်)၊ Redis lock (infra အသစ်၊ service ၃ ခု ညှိ)။

အဆင့် 2: RT Web UI (အဓိက code)

Run row insert လုပ်တဲ့နေရာ (rt_web_ui ရဲ့ tr.Open) မှာ ဒီ logic ထည့်ပါ:

① INSERT run (ယခင်အတိုင်း)
   └ အောင် → gate တွေ → noc ခေါ် (ယခင်အတိုင်း)
② 1062 ရ → key နာမည် စစ်
   ├ 'idx_pipeline_runs_run_id'        → run_id ထပ်နေတာ (ယခင်အတိုင်း error)
   └ 'uq_pipeline_runs_active_ticket'  → ③
③ ရှိနေတဲ့ run ကို ဖတ်: SELECT run_id, current_state, updated_at
                         FROM pipeline_runs WHERE active_ticket_id = ?
④ updated_at က cutoff (now − 30m) ထက် နောက်ကျ (အသက်ရှင်)
   └ "Ticket is already being processed by run X" ပြန် (outcome IN_PROGRESS) ── ရပ်
⑤ updated_at က cutoff ထက် စော (stuck) → transaction တစ်ခုထဲမှာ:
     UPDATE pipeline_runs SET current_state='FAILED_PERMANENT',
            last_state_reason='stale run closed: …', completed_at=:now, updated_at=:now
      WHERE run_id=:old AND completed_at IS NULL AND updated_at < :cutoff
     1 row ပြောင်းမှ → pipeline_run_events ထဲ 'stale_run_closed' event ရေး
⑥ INSERT ကို တစ်ခါပဲ ပြန်စမ်း
   ├ အောင် → ဆက်လုပ်
   └ 1062 ထပ်ရ (တခြား request က ဦးသွား) → ③ ဖတ်ပြီး IN_PROGRESS ပြန်
  • Key နာမည်နဲ့ ခွဲပါ: 1062 က run_id unique ကလည်း ရနိုင်လို့ error message ထဲက key နာမည် uq_pipeline_runs_active_ticket ကို စစ်မှ ticket guard ဖြစ်ကြောင်း သေချာပါတယ်။
  • ⑤ က conditional UPDATE တစ်ကြောင်း: ငါးခု ပြိုင်တူ UPDATE လုပ်ရင် row lock ကြောင့် တစ်ခုပဲ 1 row ပြောင်းပြီး ကျန်တာ 0 rows ဖြစ်ပါတယ်။ Event လည်း တစ်ကြောင်းပဲ ရေးပါတယ် (local မှာ စမ်းပြီးသား)။
  • ⑥ မှာ တစ်ခါပဲ ပြန်စမ်းပါ (loop မဖြစ်အောင်)။
  • အချိန်ကို app ဘက်က တွက်ပါ: :now, :cutoff ကို app ရဲ့ local time နဲ့ ပို့ပါ။ DB NOW() က UTC ပြန်လို့ ၆ နာရီခွဲ လွဲပါမယ်။
  • updated_at ကို သုံးပါ (created_at မဟုတ်)။ State ပြောင်းတိုင်း update ဖြစ်လို့ ရှေ့ဆက်နေတဲ့ run ကို stuck လို့ မထင်ပါ။
  • Setting: RT_WEB_UI_STALE_RUN_AFTER=30m (env)။ Retry backoff (1m+3m+5m)၊ Node-RED timeout၊ Kafka၊ rtutil ပေါင်းထားတာထက် ရှည်ရပါမယ်။
  • Exit code / UI: IN_PROGRESS ကို "No Process" လို (exit 1) သဘောထားပါ။ Error (exit 3) မဟုတ်ပါ။
  • Gate မတိုင်ခင် insert လုပ်တာ မပြောင်းပါ: NOT_ELIGIBLE ticket ကို ပြိုင်တူနှိပ်ရင်လည်း တစ်ခုက NOT_ELIGIBLE ဖြစ်ပြီး ကျန်တာ IN_PROGRESS ဖြစ်ပါတယ်။ ပြဿနာ မရှိပါ။
